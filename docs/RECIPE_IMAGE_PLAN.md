## 1. 目标与当前基础

目标：让菜谱列表、发现推荐、详情和餐桌使用与菜谱对应的成品图，保留无图与离线情况下的可用体验。建议先做 **20 道试点 → 100 道精选 → 分批覆盖 996 道**。

2026-10-20 静态检查发现：

| 位置 | 当前状态 | 所需工作 |
|---|---|---|
| `model/recipe.ets` | 已定义可选 `imageUri` | 增加缩略图/来源等约定，保留旧字段兼容 |
| `resources/rawfile/recipe.json` | 未检索到 `imageUri`；rawfile 中暂无菜品图片目录 | 建立图片清单，生成图片资源与关联数据 |

| `components/RecipeCard.ets` | 大卡/小卡已有 `Image(imageUri)`，无字段时用 emoji | 增加加载中、加载失败回退；按卡片尺寸选择图片 |

上述 `.ets` 路径相对于 `entry/src/main/ets/`。仅给 JSON 添加图片地址，当前还不能让图片沿 RDB 链路出现在卡片中。

## 2. 六步执行路线

### 第一步：建立“菜谱—图片”台账

先将当前菜谱导出为待配图清单，固定数据版本和旧下标映射。图片必须关联稳定菜谱标识，不能按下载顺序或文件夹排序对号入座。稳定 ID 迁移参见[维护指南](MAINTENANCE.md)的 M01。

建议新增受版本管理的 `content/recipe-images/manifest.json`，每条记录包括：

- 关联信息：`recipeId`、`recipeName`、图片角色（首期只做 `cover`）。
- 来源信息：来源项目/作者、原页面 URL、原图片 URL 或相对路径、上游提交、许可证或使用授权记录。
- 资产信息：原文件哈希、宽高、格式、缩略图/封面路径、生成参数版本。
- 审核信息：`pending/matched/approved/rejected` 状态、核对日期和备注。
- 展示信息：图片描述 `alt`、裁切中心（需要时）。

首期每道菜只指定一张成品封面，步骤图以后单独使用 `step` 角色，避免将原料照片当成菜品成图。

**交付物**：996 道清单及首批 20 道候选映射；记录缺图与不确定项，不把所有候选都算作覆盖成功。

### 第二步：按来源优先级收集

1. **优先匹配 HowToCook 的成品图**：固定上游提交，解析菜谱 Markdown 中的图片引用；以菜谱所在目录解析相对路径，同时保留 alt 文本和来源路径。
2. **补充团队实拍或明确允许使用的图片**：优先补齐本地特色菜及上游无图菜谱；实拍时记录菜名和原文件。
3. **仍缺图的菜保留统一占位**：台账保持缺图状态，后续内容批次逐步补齐。

匹配规则：菜名规范化只生成候选；同名菜还需核对主要原料、做法和成品外观。例如干煸四季豆与清炒四季豆不能因主料相同直接共用封面。每道菜最终成图由人工核对一次。

HowToCook 不一定覆盖本地全部菜谱，也不是每道菜都有成品图。本轮尚未统计可匹配图片数量，不预估其能覆盖多少道。仓库声明 Unlicense，复用时记录对应提交和来源；外链图单独确认其来源信息。

**交付物**：候选图片目录、缺图表、重复候选表、20 道已核对封面。

### 第三步：生成规格一致的图片

建议保留原始文件在内容素材存储中，由脚本生成 App 使用的派生图。下面是首期建议规格，须通过目标设备观感和体积测试后调整：

| 用途 | 建议尺寸（像素） | 首期体积目标 | 说明 |
|---|---|---|---|
| 小卡/餐桌缩略图 | 256 × 256 | 约 20–40 KB/张 | 用于当前 72vp 小卡及餐桌；主体居中 |
| 大卡封面 | 640 × 480 | 约 60–120 KB/张 | 4:3 派生图；实际卡片 Cover 裁切需预览 |
| 详情封面 | 长边不超过 1280 | 约 150–300 KB/张 | 按需加载，保留适当细节 |

处理步骤：纠正拍摄方向 → 统一色彩空间 → 检查主体与裁切 → 缩放 → WebP/JPEG 编码 → 去除非必要元数据 → 计算哈希。编码格式以目标 HarmonyOS 设备解码验证为准；不把低清图放大当成高清图。

命名建议：`{stableRecipeId}/{contentHash}-thumb.webp`、`-card.webp`、`-detail.webp`。哈希后缀用于图片更新时区分版本；业务仍以稳定 recipeId 关联。

**交付物**：三档派生图、规格与大小报告、用于核对“菜名 + 成图”的本地预览页。

### 第四步：打通鸿蒙图片链路

按最小改动顺序实施：

1. 在 `RecipeDBManager` 贯通现有 `imageUri`；更新 schema 及旧库升级逻辑，用一条完整菜谱验证 JSON → RDB → Repository 字段不丢失。
2. 明确资源类型。随包图片建议存放在 `entry/src/main/resources/rawfile/recipe_images/`，数据保存相对资源键，由展示层解析为 `$rawfile` 等资源对象；下载缓存使用应用沙箱路径，远端使用 HTTPS URL。不要把开发电脑路径或未经解析的 rawfile 相对路径直接传给 `Image(string)`。
3. 提取可复用的 `RecipeImage` 组件（拟新增），统一处理资源解析、占位、加载错误、圆角和裁切。菜谱 ID 或图片地址变化时重置加载状态，防止列表复用后保留上一张图的失败状态。
4. RecipeCard 小卡用 thumb、大卡用 card；详情按需用 detail；PlateCard 增加图片参数并保留 emoji 回退。
5. 清单与模型扩展多规格字段时，同步更新 RDB 写入/读取；先兼容单一 `imageUri`，再引入完整资产描述，避免一开始扩大迁移范围。

**交付物**：20 道菜全链路可见；无图、坏图、错误路径均正常回退；修改图片后更新立即可辨认。

### 第五步：确定离线与体积策略

**首期建议全部 20 道随包离线展示**，验证体验后按包体预算扩大到 100 道。不要在首期引入尚无必要的图片服务端。

量级估算：若每道菜三档图片分别为 30KB、90KB、220KB，996 道约为 **339MB** 的派生图片；仅 30KB 缩略图也约 **30MB**。这是按目标大小计算的量级，不是实际 HAP 增量，应以构建产物为准。

扩容阶段推荐：内置精选封面/缩略图与占位，长尾大图由受控对象存储或 CDN 分发并缓存。应用端不把 GitHub raw 地址作为大规模图片分发服务。

远程方案启用时补充：

- 以内容哈希作为缓存键，设置容量上限并按最近使用情况淘汰；图片更新自然生成新键。
- 限制并发下载，合并相同请求，屏幕不可见时停止不必要的预取；失败不无限重试。
- 临时文件下载完成并验证后再替换有效缓存，避免半张图成为永久缓存。
- 冷缓存断网显示占位，已有缓存断网继续显示；缓存清理与设置页行为一致。
- 资源清单与图片版本一起发布；发布前确认清单引用的文件已经存在。

**交付物**：实测 HAP 增量、缓存预算、离线回归记录。图片体积小不代表解码内存小，长列表还需测量内存峰值和滚动情况。

### 第六步：批量补齐与验收

| 批次 | 内容范围 | 验收要求 |
|---|---|---|
| A：20 道试点 | 选不同颜色、形状、汤/主食/荤素，含横竖图及至少一个缺图/坏图案例 | 对图、裁切、字段持久化、升级、失败回退均通过 |
| B：100 道精选 | 按首页曝光菜、维护者精选菜单、常见家常菜排序；有真实使用数据后再按频次优化 | 清单中每张已核对；包体预算内；全页面展示一致 |
| C：剩余 896 道 | 每批 50–100 道，按分类推进；无匹配项保留缺图状态 | 每批有覆盖率、错配/坏链检查、增量包体和回归记录 |

覆盖率按“有已核对且可加载的成品图的菜谱数 / 当前有效菜谱数”统计。分类占位、emoji、重复误配图不计入成图覆盖率。

每批至少检查：

- 图片与菜名、主要食材、烹饪方式一致，成品图和过程图区分正确。
- 素材来源、哈希、尺寸齐全，引用的本地文件或远端对象存在。
- 首页卡片、发现、详情、收藏/餐桌展示正确，暗色主题和裁切正常。
- 无图/坏图/断网/缓存清理后正常回退；快速滚动不会串图。
- 覆盖升级后收藏仍指向原菜，图片更新不复用旧内容。
- 记录同设备补图前后的首屏时间、滚动情况、内存峰值和 HAP 大小，作为下一批扩容依据。

### 网络通路结论

`raw.githubusercontent.com` 被墙；可用 `api.github.com`（git/trees + contents 均 200）与 `cdn.jsdelivr.net/gh`（图片下载偶发连接重置）。抓取实现最终**走 `api.github.com` contents API 取 base64**，稳定可靠。

### 覆盖现实（重要）

固定提交 `f6da4528` 的 HowToCook 仅含 **197 道菜**（`dishes/` 下 `.md` 目录数），其中有图 177 道；与本地 `recipe.json`（996 道，去重自 1511）**精确菜名命中仅 28 道**，其中 27 道有图、26 道可用（`土豆炖排骨` 的 `排骨*.jpg` 为 Markdown 未引用的孤儿文件，剔除）。
