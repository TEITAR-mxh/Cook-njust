# HowToCook 借鉴与优化路线

## 1. 方向结论

建议将 App 的主线收敛到 **“现有食材 → 选一餐 → 补齐缺料 → 按步骤做完”**。现有项目已有搜索、餐桌、导出清单和烹饪模式，最有收益的投入是把这条流程的数据和语义打通。

HowToCook 的主要价值是可维护的菜谱内容规范：原料与工具、明确用量、操作步骤、附加说明，以及分类目录和贡献校验。它的 Markdown 菜谱不能直接视为本 App 的结构化数据库。

调研日期：2026-10-20；调研期间远端 `master` HEAD 为 `f6da4528c4cb55fe0fbb5c3db17d76202b9f6ad9`。本轮阅读的是 `master` 文档，实际导入时应检出并固定具体提交，生成对应来源记录。

## 2. 借鉴内容与本地落点

| HowToCook 依据 | 本地已有基础 | 推荐增量 | 优先级 |
|---|---|---|---|
| 模板的“必备原料和工具 / 计算 / 操作 / 附加内容” | `stuff`、`tools`、`steps`、详情弹窗 | 补原始份量、用量、提示和来源；校验步骤中出现但原料表遗漏的材料 | P0/P1 |
| 明确 g/ml、时间或步骤完成标准 | 用量换算、烹饪 Swiper | 范围用量、结构化时间、熟度判断；先展示，再考虑计时提醒 | P1 |
| 素菜/荤菜/水产/早餐/主食等目录 | 难度、烹饪方式筛选 | 新增独立菜品分类，避免将“早餐”和“炒”混成同一维度 | P1 |
| “如何决策吃什么”的人数和荤素搭配 | 随机推荐、今日餐桌 | 可编辑的一餐建议、重复主料降权、候选不足解释 | P1 |
| `tips/` 厨房准备与技法说明 | 专注烹饪步骤 | 在“焯水”等步骤关联简短技巧卡，离线可读 | P2 |
| 菜谱模板、Markdown/textlint、自定义检查 | 本地 JSON 检查与少量 Hypium 用例 | 受版本管理的数据校验、差异报告和可复现导入 | P0 |

上游的“人数 + 1 道菜、荤菜略多或相等”是其选菜启发式。App 可把它作为用户可改的套餐起点；不作为营养达标判断，也不直接覆盖用户的饮食偏好。

## 3. 数据接入方案（待实现）

### 3.1 先做小样本

选取 10–20 道覆盖多分类的菜谱，包含单文件、带图片目录、范围用量、可选材料、多份配方和带链接步骤的样本。先完成一次导入、展示和更新闭环，再评估扩容。

```text
固定提交的 HowToCook 内容
  → Markdown 解析（标题、列表、图片、链接）
  → 中间数据（保留原文、来源、无法确定的字段）
  → 规范化与校验
  → 新增/修改/删除/冲突报告
  → 合并本地修订，生成版本化 recipe bundle
  → App 迁移与 RDB 导入
```

推荐在开发/构建阶段生成数据包，App 继续使用离线 JSON/RDB。一次同步应能用相同上游提交、转换器版本和本地修订重复生成相同内容。

### 3.2 字段设计建议

以下均为拟新增或扩展字段，当前模型尚未实现：

| 字段/约定 | 用途 |
|---|---|
| 不可复用的稳定 `id` | 保持现有数字引用体系，维护分配表；不要由数组位置或菜名重新生成 |
| `source.provider/path/revision/url` | 标识 HowToCook 来源、路径和提交；路径改名通过映射保留原 ID |
| `category` | 独立的菜品分类，与 tags、methods 分开 |
| `baseServings` 与基准说明 | 定义原配方份量；明确一份可供几人食用后再做人数换算 |
| `ingredients` | 规范名称、原始文本、数值/区间、单位、是否可选、是否常备调料 |
| `stepDetails` | 步骤文本、可确认的时长、火候、完成判断、关联图片；兼容旧 `steps` |
| `tips` | 保留原文附加说明和技法链接 |
| 营养来源与计量基准 | 区分估计热量、每份/每 100g；未知营养素保持缺失 |
| bundle 版本/哈希、转换器版本 | 支持增量比较、问题回溯和升级测试 |

注意转换边界：

- 上游将原料和工具放在同一章节，并允许省略厨房常备项，不能把这一章节每一行都直接写进 `stuff`。
- “可选”材料不能阻断生存模式；常备调料应由用户配置是否默认拥有，不能静默认为全部具备。
- 上游 1–5 星与本地“简单/普通/困难”不同，可先保留原星级，再明确展示映射规则。
- 时间可能在描述或步骤中，不能无条件把所有等待时间相加作为总用时；缺失时显示未知。
- Markdown 中的相对图片路径应以原菜谱目录为基准解析。步骤列表要保留嵌套说明、图片顺序与链接含义。
- 模板中的预计卡路里不等于完整营养表；不能据此填充蛋白质、脂肪、钠等未知值。
- 本地已有同名菜不应自动覆盖。按来源标识比较，菜名相近项进入冲突报告，并保存本地修订。

### 3.3 兼容和校验

先完成维护指南 M01/M02。旧用户数据依赖数字下标，导入新 ID 必须有版本化映射；对支持升级的每个历史数据包保留其映射。仅用新版本数组位置或菜名反推旧引用不可靠。

第一批校验建议：

1. ID 唯一、类型合法、不可误复用；来源路径/提交齐全。
2. 菜名、必需原料、步骤非空；字段类型、难度、分类符合约定。
3. 用量为数值或合法区间；单位可识别，无法识别项保留原文。
4. 输出疑似“步骤新增食材”清单供人工核对，明确常备调料例外；不能只凭字符串匹配强行判错。
5. 图片路径可解析；新增/变更/删除数量在报告中可见。
6. 样例字段经过真实 RDB 往返不丢失；旧版用户记录迁移后仍指向原菜。

## 4. 面向“美食选择”的体验优化

### A. 让筛选结果解释得清楚

在 `RecipeSearchService` 和统一食材规范化基础上，为卡片展示“已有 4/5 种必需食材、缺鸡蛋、需要炒锅”。新增“只差 1–2 样”的候选区；硬条件不满足时解释原因并允许用户调整。

验收：空结果不擅自放开厨具/排除食材限制；别名在搜索、详情、清单中得到同样判断。

### B. 从随机一道菜升级为可编辑的一餐

复用今日餐桌，支持人数、菜数、荤素偏好和可用厨具；先按约束生成候选，再按缺料数量、主料多样性、近期重复情况排序。允许锁定一道菜后只换其余菜。

验收：不重复选同一菜；候选不足时返回可解释的部分结果；用户可修改套餐，重启后保留选中结果。用时/预算筛选应在字段足够完整后接入。

### C. 合并一餐的采购清单

将单菜缺料导出扩展为多菜聚合：先统一别名和份量，再合并相同原料的兼容单位。同一原料 `500g + 1kg` 可以换算；`2个 + 200g` 没有重量依据时分项显示。

验收：区间用量正确相加；不可换算的项保留；改人数后清单一致更新；菜谱已删除或字段不完整时不产生错误合计。

### D. 帮助新手完成操作

在现有 `CookingFocusView` 上逐步补充“开始前检查”、每步完成标准、暂停/恢复和已完成状态。有明确时长的步骤再增加计时；计时功能单独验证前后台恢复和通知行为。

验收：未知时长不生成虚假的倒计时；退出后屏幕常亮释放；切换步骤不丢失当前烹饪进度。

## 5. 建议维护顺序

| 批次 | 可拆分工作 | 完成标准 |
|---|---|---|
| 第 1 批：维护基线 | 共享数据校验；确认三模式契约；确定 ID 与字段迁移方案 | 新克隆可校验；错误样例可被检出；迁移映射可审阅 |
| 第 2 批：正确性修复 | ID 迁移；RDB 字段贯通；统一别名；份量/范围换算 | 覆盖升级保留用户引用；完整样例字段往返通过；边界用例通过 |
| 第 3 批：HowToCook 试点 | 固定提交导入 10–20 道；来源展示；差异报告 | 可重复生成；同名不误覆盖；可离线烹饪 |
| 第 4 批：选餐闭环 | 缺料解释；一餐建议；多菜采购清单 | 选餐→采购→烹饪能完成，核心回归通过 |
| 第 5 批：性能与扩容 | 测量后拆分页面/懒加载；扩大内容样本；技巧卡 | 有同设备前后数据，内容质量无回退 |

推荐第一个修复任务从 M03（搜索模式）和 M04（统一食材匹配）入手：范围较小，效果直接。涉及菜谱增删、排序或外部导入的任务必须先完成 M01/M02。

菜品图片可作为并行内容工作开展，采集和整理先行，入库上线依赖 ID 与字段贯通。完整执行顺序见[菜品图片补齐工作路线](RECIPE_IMAGE_PLAN.md)。
